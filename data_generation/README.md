# TriggerBench Data Generation

TriggerBench tests **prospective memory** in LLM agents: whether a model can encode an implicit (main setting) constraint mentioned in passing, retain it through later conversation, and intervene (or stay silent) at the right moment — without ever being told “remind me” explicitly.

This directory holds the construction package for four of the five paper dimensions. Each dimension starts from a small set of human-authored seed blueprints and expands them into timestamped dialogues with contrastive variants (Positive-Clean, Positive-Overloaded, and, where applicable, Negative-Clean).

| Dimension | Directory | Paper | What is latent |
|-----------|-----------|-------|----------------|
| State-Tracking | [`state_tracking/`](state_tracking/) | §3.2 Dim 1 | An implicit physical / logical state change |
| Temporal Grounding | [`temporal_grounding/`](temporal_grounding/) | §3.2 Dim 2 | A strict point-in-time commitment |
| Logical Adherence | [`logical_adherence/`](logical_adherence/) | §3.2 Dim 3 | A user-stated conditional policy |
| Attention Recovery | [`attention_recovery/`](attention_recovery/) | §3.2 Dim 4 | An in-progress Task A, displaced by an orthogonal interruption |

Design details (seed matrices, validity rules, dimension-specific constraints) live in each folder’s README. File layout for the runnable package is in [Construction pipeline](#construction-pipeline).

Safe Coding is not generated by the pipeline below. The scenarios are mainly hand-authored constraint/trigger pairs (developer shortcut → later deploy/merge action). The conversation in between is a real **Terminal-Bench 2.0** agent trajectory ([Merrill et al., 2026](https://arxiv.org/abs/2601.11868); trajectories: [yoonholee/terminalbench-trajectories](https://huggingface.co/datasets/yoonholee/terminalbench-trajectories)), not involving LLM-written thematic turns, so the dialogue format and construction process differ from the other four dimensions and involve substantially more manual work. 

We therefore release the Safe Coding evaluation data directly with the TriggerBench dataset, rather than a generation package in this folder.

## Construction pipeline

The four dimensions above share the same staged construction. 

Every scenario follows \( C $\xrightarrow{\Theta}$ T $\to$ A \): a latent **Constraint**, orthogonal thematic turns \(\Theta\), a **Trigger**, and a required **Action** (or silence on the negative variant).

Not every dimension uses all five stages as Temporal Grounding and Attention Recovery have no Negative-Clean variant. Stage internals differ slightly by dimension specific designs.

```
data_generation/
├── shared/                          # Cross-dimension utilities
│   ├── llm_client.py                # OpenAI-compatible chat client (env-based)
│   ├── json_utils.py                # JSON extraction / saving
│   └── time_utils.py                # Duration parsing and timestamps
└── dimension/                       # Runnable reference
    ├── seeds/
    │   ├── blueprints.py            # Human-authored seed blueprints
    │   └── user_dialogues.py        # Few-shot user dialogue(s) for Stage 2
    ├── pipeline/
    │   ├── generate_blueprints.py           # Stage 1
    │   ├── generate_user_dialogues.py       # Stage 2
    │   ├── complete_dialogues.py            # Stage 3 (Positive-Clean)
    │   ├── derive_overloaded_variant.py     # Stage 4 (Positive-Overloaded)
    │   └── derive_negative_variant.py       # Stage 5 (Negative-Clean)
    ├── scripts/                     
    └── outputs/                     
```

### Stage 1 — Blueprint design (`generate_blueprints.py`)

An LLM writes new scenario skeletons on that dimension’s combinatorial matrix, using the human seeds as in-context exemplars.

Each blueprint records the latent constraint, the trigger, timing, and gold labels (intent + slot aliases). Some fields are needed by later stages for variants (e.g., `distracting_task` for Positive-Overloaded; `resolution_for_negative` if Negative-Clean exists). Constraints are stated as ordinary narration, not as an instruction to remember.

### Stage 2 — User-dialogue stretching (`generate_user_dialogues.py`)

Each blueprint becomes a **user-only** dialogue. For instance, the State-Tracking template is:

```
[Thematic ×2–5] → [Constraint ×1] → [Thematic ×2–5] → [Trigger ×1]
```

Thematic turns stay in the scenario’s domain but should not spell out the gold action. Timestamps should respect the blueprint’s time gap (small tolerance). No assistant utterances are written in this stage.

### Stage 3 — Positive-Clean (`complete_dialogues.py`)

Assistant replies are filled in for every user turn except the trigger. Replies should stay non-proactive: they help with the current ask and try to avoid leak the reminder before the trigger.

The resulting dialogue is the Positive-Clean evaluation item: at the trigger, the agent should act.

### Stage 4 — Positive-Overloaded (`derive_overloaded_variant.py`)

The Positive-Clean trigger is kept as an exact prefix. A distracting, concurrent request is appended on the same user turn (from `variations.distracting_task`). All earlier turns are unchanged.

This tests whether the agent still acts on the latent constraint when the trigger turn also contains a concurrent ask or request.

### Stage 5 — Negative-Clean (`derive_negative_variant.py`)

Used where a coherent “risk already gone / rule not met” case exists. A resolution event is inserted between constraint and trigger or the state-flipping is performed, so that at trigger time the agent should stay silent.

An always-remind policy fails this variant. Together with Positive-Clean it is a sensitivity / specificity pair.

## Running

Set your API before running.
```bash
cd state_tracking
bash scripts/run_stage1_blueprints.sh
bash scripts/run_stage2_user_dialogues.sh
bash scripts/run_stage3_positive_clean.sh
bash scripts/run_stage4_positive_overloaded.sh
bash scripts/run_stage5_negative_clean.sh
```

Pass `--model` (or `MODEL=` on the scripts) for whatever API you have. **A stronger model generally yields better data.**

**Put the budget on Stage 1 and Stage 2.** Those stages invent the skeleton and stretch it into a schema-valid, implicitly worded, timestamped user dialogue. Weaker models fail the checks more often, and accepted outputs tend to be generic. We recommend **GPT-5.4 or a stronger model** as the minimum for these two stages.

**Later stages are cheaper to downgrade if needed.** They edit the pre-generated skeleton (assistant replies; a distractor suffix; a polarity/resolution edit). If resources allow, using the strong model for every stage is still better.
